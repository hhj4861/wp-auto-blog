TypeSafe Jev는 무엇을 판단하는 모델일까?

Jev는 긴 답변을 쓰기보다, 프로그램이 바로 사용할 수 있는 선택·점수·확률을 반환하도록 설계된 모델입니다. TypeSafe는 이를 System One 모델이라고 부릅니다. 고객 문의 분류나 자료의 관련성 평가처럼 범위가 정해진 판단에 주목할 만합니다. 다만 정해진 형식으로 답한다는 보장과 판단 내용이 언제나 맞는다는 보장은 다릅니다.

AI가 답변은 잘하는데 자동화 프로그램에 붙이면 파싱 오류나 애매한 결론 때문에 멈추는 경우가 있습니다. Jev는 이런 지점에 다른 접근을 제안합니다. 이 글은 TypeSafe 공식 문서에 근거한 개념·도입 안내이며, 직접 API를 호출해 검증한 사용 후기는 아닙니다.

1. 생성 모델과 판단 모델의 차이

TypeSafe는 2026년 9월 15일 Jev를 공개하며 비정형 입력 상태를 받아 정해진 구조의 확률적 결정을 반환한다고 설명했습니다. 자유로운 문자열 생성을 포기하고, 소프트웨어가 사용할 판단에 집중하는 접근입니다. TypeSafe 공식 출시 발표

필요한 일 어울리는 접근 결과의 예
독자를 설득하는 설명문 작성 텍스트 생성 모델 자연어 문서·답변
문의의 담당 부서 선택 구조화된 판단 미리 정한 선택지와 확률
자료를 읽고 답변 작성·검토 생성과 판단을 조합 초안과 검토용 점수

위 표는 역할을 이해하기 위한 편집부의 구분입니다. 일반 LLM도 구조화된 출력을 낼 수 있습니다. Jev의 차별화 주장은 판단용 출력과 처리 방식에 집중한 설계에 있으며, 모든 작업에서 생성 모델을 대체한다는 의미는 아닙니다.

2. Choice·Score·Noul을 이해하면 쓰임새가 보인다

공식 문서는 세 가지 기본 질문 유형을 소개합니다. 입력 자료는 state, 묻고 싶은 항목은 questions에 해당합니다. Jev 개요 문서

유형 질문 방식 공식 반환 항목
Choice 주어진 선택지 중 무엇인가? choice, probabilities, confidence
Score 정해진 평가 기준에서 어느 수준인가? score, probabilities, confidence
Noul 어떤 진술이 참인가? 0~1 범위의 noul 값

예를 들어 문의 내용을 입력하고 ‘결제·기술·영업 중 어느 부서인가’를 Choice로, ‘긴급성은 어느 수준인가’를 Score로 나눠 물을 수 있습니다. 공식 문서상 질문들은 같은 상태를 대상으로 병렬·독립 평가됩니다. 따라서 한 질문이 다른 질문의 답을 읽고 순서대로 추론한다고 가정하면 안 됩니다.

복잡한 판단은 요소별로 나누고 최종 조합은 코드에서 처리하라는 것이 문서의 권장 방향입니다. ‘이 글을 무조건 발행해도 되나’처럼 여러 기준이 섞인 질문보다 ‘공식 출처가 있는가’, ‘기간이 유효한가’, ‘핵심 질문에 답하는가’를 구분하는 식입니다.

3. confidence 0.9가 정확도 90%라는 뜻일까?

그렇게 바로 해석하면 안 됩니다. TypeSafe 문서의 confidence는 Choice·Score의 확률 분포가 얼마나 한쪽으로 모였는지를 요약한 값입니다. 균등하게 퍼진 분포에서는 낮고, 하나의 결과에 집중되면 높아집니다. Noul에는 같은 confidence 필드가 붙지 않습니다. 확률과 confidence 공식 설명

높은 자신감으로 틀리는 경우까지 확인하려면 실제 업무의 정답 자료가 필요합니다. confidence 기준을 0.9로 정했다는 사실만으로 ‘오류가 10% 이하’라고 말할 수는 없습니다. 임계값은 업무별 평가 결과와 오판의 비용을 함께 보고 정해야 합니다.

예를 들어 자동 분류를 잘못해도 담당자가 바로 바꿀 수 있는 문의와, 외부에 잘못된 정보를 공개하는 판단은 영향이 다릅니다. 같은 점수 기준을 모든 자동화에 복사하기보다, 낮은 신뢰도나 자료 부족을 사람이 볼 별도 경로로 보내는 편이 검증하기 쉽습니다.

4. ‘환각 없음’과 ‘오판 없음’을 구분하자

출시 발표가 강조하는 형식 보장은 미리 정의한 구조와 선택지에서 결과를 낸다는 의미로 읽어야 합니다. 선택지가 A·B·C라면 존재하지 않는 D라는 문자열을 만들지 않는 것과, 실제 정답인 B를 고르는 것은 서로 다른 문제입니다. 형식 안전성과 평가 조건 설명

판단에 필요한 최신 자료를 주지 않았거나, 서로 겹치는 선택지를 만들었거나, 평가 기준이 모호하면 올바른 형식의 잘못된 결과를 받을 수 있습니다. Jev를 붙였다는 이유만으로 출처 검증이나 예외 처리가 사라지지는 않습니다.

5. 193.6배 빠르고 444.6배 저렴하다는 수치는?

이 숫자는 TypeSafe가 공개한 특정 워크플로 평가 결과입니다. 회사도 실제 환경에서 기대할 수 있는 개선 폭의 높은 쪽에 해당할 수 있다고 설명합니다. 평가의 기준 확률은 다른 대형 모델들의 답을 이용하며, 모든 사례의 절대적인 정답표와 같지 않습니다. 입력 길이, 비교 모델, 네트워크 위치, 질문 구성에 따라 차이가 달라집니다. 벤치마크 방법과 한계

공식 홈페이지에는 입력 10억 토큰당 42달러라는 가격이 안내돼 있습니다. 실제 비용을 산정할 때는 최신 요금과 계정 조건을 다시 확인해야 합니다. 저렴한 호출 비용뿐 아니라 재시도, 사람의 검토, 연동 개발에 드는 비용까지 포함하세요. TypeSafe 공식 가격 안내

6. 처음 검증할 때 추천하는 방법

  1. 작은 판단 하나 선택: 예를 들어 ‘기술 문의인가’처럼 정답을 확인하기 쉬운 과제를 정합니다.
  2. 익명 예시 준비: 명확한 사례, 경계 사례, 정보가 부족한 사례를 함께 모읍니다.
  3. 공식 Playground에서 확인: state와 질문 유형을 입력하고 결과를 비교합니다. 실제 API 연동은 공식 문서의 인증·요청 형식을 따릅니다.
  4. 오류와 보류를 분리: 잘못된 판단, API 실패, 판단 유보를 각각 기록합니다.
  5. 운영 적용 전 기준 확정: 자동 처리할 조건과 사람이 검토할 조건을 검증 자료에 맞춰 결정합니다.

Playground와 API 시작 경로는 공식 Quick start에서 확인할 수 있습니다. 문서가 연결하는 콘솔은 console.typesafe.ai입니다. 이름이 비슷한 비공식 안내 사이트에 API 키를 입력하지 마세요.

도식으로 이해하기: Jev가 맡는 판단과 프로그램이 맡는 실행

판단 모델을 넣는다고 자동화의 책임이 모두 모델로 넘어가는 것은 아닙니다. 입력 자료를 준비하고 질문을 설계하는 일, 나온 결과를 어떤 행동으로 연결할지 정하는 일은 별도로 남습니다. 이 경계를 분명하게 만들면 틀린 답변뿐 아니라 통신 오류, 자료 누락, 사람이 확인해야 할 상황도 서로 다르게 처리할 수 있습니다.

이 도식은 공식 시스템 화면이 아닌 편집부의 설계 예시입니다. Jev는 문의를 어떤 부서로 보낼지 판단하는 데 쓰고, 실제 티켓 이동은 별도 프로그램이 수행하는 구조입니다. 환불처럼 별도의 권한과 확인이 필요한 행동을 분류 결과 하나만으로 실행하도록 연결하지 않는 것이 좋습니다.

실전 예시: 고객 문의 한 건을 세 가지 질문으로 나누기

다음 문장을 가상의 고객 문의로 사용해 보겠습니다. “같은 주문이 두 번 결제된 것 같아요. 로그인은 되지만 주문 번호를 찾지 못했습니다.” 이는 설명을 위해 만든 입력이며 실제 Jev 호출 결과가 아닙니다. 이 한 문장에 “잘 처리해줘”라고 요청하는 대신 담당 부서, 긴급도, 추가 정보 필요성을 나누어 정의할 수 있습니다.

질문유형·기준의 예결과를 사용할 곳
어느 부서의 확인이 필요한가?Choice: 결제 / 기술 / 영업 / 기타·판단 보류검토 대기열 선택
처리 우선순위는 어느 수준인가?Score: 일반 문의 / 업무 일부 차질 / 즉시 확인할 중대한 문제같은 대기열 안에서 확인 순서 조정
주문 식별 정보가 충분한가?Noul: 입력에 주문을 식별할 정보가 있는지추가 정보 요청 여부 검토

위 예시에서는 사람이 읽으면 결제 담당자의 확인이 필요하다고 예상할 수 있지만, 그것을 실제 모델 응답처럼 표시하지는 않습니다. 실제 평가에서는 모델이 반환한 값과 사람이 정한 정답을 따로 기록해야 합니다. 문의에 “로그인”이라는 단어가 있다는 이유로 기술 문의로 보내는 오류가 발생하는지도 확인할 수 있습니다.

좋은 기준에는 경계 사례와 보류 선택지가 있다

“긴급도를 1부터 5로 평가해줘”만으로는 점수의 의미가 모호합니다. 매출 영향인지, 이용 불가 시간인지, 개인정보 노출 가능성인지 먼저 정해야 합니다. 처음에는 서로 겹치지 않는 적은 수의 수준으로 시작하고, 각 수준에 해당하는 예시와 해당하지 않는 예시를 함께 정리하는 편이 좋습니다.

선택지에 정답이 없으면 가장 비슷한 틀린 답을 고를 수 있습니다. 문의 분류라면 “기타” 또는 “판단 보류” 경로를 설계하고 그 결과를 사람이 확인하도록 연결하세요. 다만 보류 선택지를 넣는다고 오판이 사라지지는 않습니다. 명확한 문의까지 과도하게 보류하는지도 실제 데이터로 살펴봐야 합니다.

또한 같은 호출의 질문들이 서로의 답을 순서대로 참고한다고 가정하면 안 됩니다. 공식 소개 문서는 질문들이 같은 입력 상태에서 독립적으로 처리된다고 설명합니다. “먼저 고른 부서에 따라 다음 질문을 바꾸기”가 필요하다면 코드를 통해 결과를 조합하거나 다음 호출을 별도로 구성해야 합니다.

숫자로 풀어보기: 선택 확률 0.6인데 confidence는 왜 0.4일까?

아래는 Choice의 계산 방법을 보여주는 가상의 분포입니다. 실제 서비스 성능을 나타내는 숫자가 아닙니다. 선택지가 셋이고 모델이 부여한 확률이 결제 0.6, 기술 0.3, 영업 0.1이라고 해보겠습니다.

공식 confidence 문서에서 Choice는 선택지 수를 n, 가장 큰 확률을 p라고 할 때 (p − 1/n) ÷ (1 − 1/n)으로 계산합니다. Score는 점수 사이의 순서를 고려하므로 같은 식을 적용하지 않습니다. Noul에는 별도의 confidence 항목이 없습니다. 따라서 서로 다른 유형의 숫자를 이름만 비슷하다고 한 기준으로 섞어 쓰면 안 됩니다.

이 예시에서 확인해야 할 질문은 “0.4면 무조건 실패인가?”가 아닙니다. 우리 문의 데이터에서 어떤 분포일 때 잘못 분류하는지, 잘못 분류했을 때의 손실이 얼마나 큰지입니다. 담당 부서를 바꾸는 정도의 되돌릴 수 있는 처리와 고객에게 돈을 보내는 행동은 같은 임계값으로 판단할 일이 아닙니다.

불확실한 판단과 API 오류를 같은 실패로 취급하지 말자

상황의미복구 방향
정상 응답이지만 판단이 애매함자료나 질문만으로 확신하기 어려움추가 정보 요청 또는 사람 검토
필수 응답을 받지 못함통신·인증·제한·서비스 오류 가능성오류 종류와 재시도 가능 여부부터 확인
높은 confidence인데 정답과 다름확신을 가진 오판입력·선택지·평가 데이터와 임계값 재검토
판단은 맞았지만 실행이 실패함후속 시스템에서 문제가 발생판단 결과를 보존하고 실행 상태를 확인

예를 들어 응답을 받지 못한 요청을 “낮은 점수”로 저장하면 모델이 실제로 낮게 평가했는지 API가 실패했는지 구분할 수 없습니다. 운영 기록에는 요청 식별자, 사용한 질문 정의의 버전, 성공·실패 유형, 판단값, 실제 실행 결과를 분리해서 남기는 편이 좋습니다. 민감한 문의 원문은 필요한 범위에서만 다루고 접근을 제한해야 합니다.

후속 처리 의사코드: 판단값을 행동으로 바꾸기

# 설명용 의사코드. 실제 Jev SDK 호출 문법이 아닙니다.
if not response_received:
    record_api_error()
    retry_only_if_appropriate()
elif missing_required_input:
    request_more_information()
elif requires_human_approval or uncertain_for_this_task:
    send_to_review_queue()
else:
    route_ticket_once()
    verify_ticket_destination()

여기에는 고정된 confidence 숫자를 넣지 않았습니다. 자료 없이 특정 기준을 정답처럼 제시할 수 없기 때문입니다. 실제로는 검증 데이터에서 기준을 선택하고, 외부에 영향을 주는 행동에는 별도 승인 조건을 둡니다. 실행 후 응답이 끊겼다면 무작정 다시 이동·발송하기보다 이미 처리됐는지 조회해 중복을 막아야 합니다.

도입 전 검증: 정확도와 자동 처리 비율을 함께 보자

처음에는 익명화한 실제 문의를 모아 명확한 사례, 여러 의도가 섞인 사례, 정보가 부족한 사례로 나누어 볼 수 있습니다. 사람이 붙인 정답도 의견이 갈리는지 확인해야 합니다. 질문과 임계값을 고를 때 쓴 데이터와 최종 성능을 확인할 데이터는 분리해야 유리한 예시만 맞춘 결과를 피할 수 있습니다.

가령 검증용 200건 중 120건을 자동 분류하고 그중 114건이 맞았다면, 자동 처리 구간의 정확도는 95%, 전체 중 자동 처리 비율은 60%입니다. 이 숫자는 지표 해석을 위한 가정이며 Jev의 벤치마크가 아닙니다. 95%만 보고 나머지 80건의 검토 부담을 빼면 실제 운영 비용을 놓칩니다.

반대로 자동 처리 비율만 높이면 잘못된 처리가 늘 수 있습니다. 두 지표와 함께 심각한 오분류 수, 사람 검토 시간, API 오류율, 느린 요청의 지연시간을 기록하세요. 비용도 모델 호출료만 비교하기보다 입력 준비·재시도·검토에 든 비용까지 포함하는 편이 현실적입니다. 판단 모델의 도입 가치는 예쁜 JSON이 아니라 이후 업무가 더 정확하고 관리하기 쉬워졌는지로 평가해야 합니다.

AI 에이전트와 함께 쓰면 무엇이 달라질까?

편집부가 제안하는 구조는 자료 수집 → 범위가 정해진 판단 → 콘텐츠 생성 → 근거 검토 → 승인·실행입니다. Jev는 이 가운데 작은 판단 단계의 후보가 될 수 있습니다. Muse나 Dots처럼 전체 작업을 이어가는 에이전트와는 역할이 다릅니다.

중요한 것은 특정 모델 하나로 모든 실패를 해결하겠다는 기대보다, 어디에서 무엇을 판단했고 실패했을 때 어떻게 복구할지 드러나는 구조입니다. 한국어 업무 데이터에서의 정확도와 응답 시간은 직접 측정해야 합니다. 형식 오류 감소가 실제 업무 오류 감소로 이어지는지를 확인하는 것이 도입의 핵심입니다.

표지는 AI로 제작한 개념 일러스트이며 실제 제품 화면이 아닙니다. 활용 구조와 검증 절차는 편집부 제안이며 성능 보장이 아닙니다.
