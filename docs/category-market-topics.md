# 카테고리별 시장 키워드 → 예약 발행

기존 11시 스케줄은 유지한다: 월·수·금 생활정보, 화·목 취업, 토 건강.
매일 09:30에는 각 카테고리를 독립적으로 탐색해 보고서만 생성한다. 11시 발행 작업은
해당 카테고리의 36시간 이내 보고서를 읽고 검색 근거·주제 적합성·WordPress 중복 여부를 다시 확인한다.
보고서가 없거나 후보가 소진되었으면 그 자리에서 새로 탐색한다.

## 선정 근거

1. 취업·생활정보·건강별로 검색 범위를 정하는 시드를 분리한다. 시드는 발행 주제가 아니다. 연관 검색어가 다른 분야로 확장될 수 있으므로 명확한 분야 단어로 후보 풀을 먼저 분리하고, 근거 검토에서 검색어와 본문의 주된 목적을 다시 분류한다. 국가기술자격·직업 자격증은 취업, 건강보험 환급은 건강, 세금·주거·생활요금은 생활정보다. 포괄적인 신청·조회라는 이유로 생활정보에 넣지 않는다. 의료 직종 자격증은 취업이 우선한다. 분류 단어가 없는 검색어는 공식 본문 검토로 판정하며, 명확한 분야 불일치는 생성 제목과 캐시 재사용 시에도 거부한다.
2. 네이버 검색광고 API가 실시간 반환하는 연관 키워드·월 PC+모바일 검색량에서 신규 후보를 수집한다. AI가 시장 검색량이나 검색 결과를 만들어내지 않는다.
3. 건강 카테고리는 CAK의 최근 24시간 이내 일별 검색 지표도 합친다. 직접 급상승 후보와 그 시드에서 새로 조회한 연관어를 조사 대상에 섞는다. 월량·상승률·만료 검증 및 연결 방식은 [CAK 브릿지](cak-bridge.md)를 따른다. 최소 500회 이상의 실측 후보에서 발행 이력을 먼저 제외한다. 검색량 상위 후보와 구체적인 질문·조건·서류·준비물 등의 중소 검색량 후보를 섞어 최대 120개를 탐색 대상으로 만든다. 검색량 상위 60개만으로 후보를 제한하지 않는다.
4. 공개 글·초안·예약 글 제목과 API에 노출된 SEO 초점 키워드, 기존 레지스트리, 완료된 큐, 누적 키워드 이력을 대조한다. 조회 실패를 미발행으로 해석하지 않는다. 한 번의 전체 카테고리 탐색에서도 먼저 선정된 키워드는 이후 카테고리에서 제외한다.
5. Codex는 먼저 실측 목록에서 조사할 검색어만 고른다. 최대 2회, 회당 6개를 조사하며, 출처 실패 등으로 선정 수가 부족하면 조사하지 않은 다른 후보를 고른다. AI가 제목이나 출처 URL을 먼저 지어내게 하지 않는다.
6. 예약 선정과 큐 발행은 `MARKET_SEARCH_PROVIDER=codex_native_search`로 Codex App Server의 실제 검색 결과 URL·제목·발췌문을 읽는다. 모델이 작성한 답변에서 검색 결과를 추출하지 않는다. 요청한 검색어·thread·turn과 연결된 완료 이벤트의 첫 10개 결과 위치에서 유효한 자료만 사용하고 실제 제공자를 기록한다. 같은 도메인의 여러 결과도 각각 표본 비중에 반영한다. 이 결과는 Google 검색 순위가 아니다. 월 5만 회 이상이면서 정부·대형 사이트 비중이 40%를 넘는 키워드는 제외한다. 표본이 없으면 월 5만 미만의 구체적인 질문형 키워드만 공식 본문 조사로 넘기며, 검색 표본 없이 발행하지 않는다. 제공자 설정이 없을 때의 기존 Google→DuckDuckGo 경로는 유지하지만, 명시한 Codex 경로가 실패하면 다른 제공자로 자동 변경하지 않는다.
7. 검색 결과의 공식 URL과 공식 도메인 제한 검색으로 찾은 URL의 본문을 읽는다. 공식 자료가 없으면 Codex 내장 웹검색으로 보충한다. Codex 경로는 JSONL의 완료된 `web_search/search` 활동을 확인하고, 열람 이벤트의 주소(`native_open`) 또는 모델이 보고한 주소 후보(`model_reported_locator`)를 별도 HTTP 요청으로 검증한다. 모델이 보고한 주소는 위치 후보일 뿐 색인·검색 순위·Codex 방문 증거가 아니다. 실제로 가져온 공식 본문만 근거로 인정하며, 본문 없이 모델이 작성한 요약이나 URL만으로는 통과하지 않는다. 그 후 검색 의도·카테고리·독자 가치·근거·마감을 검토해 제목을 확정한다. 순위 자료가 없는 경우 공식 본문에서 확인할 수 있는 질문과 독자 가치만 검토하며 경쟁 우위를 주장하지 않는다.
8. 수요(log 스케일, 최대 35점), 대형 사이트가 적은 검색 결과의 비중(최대 40점), 검색결과로 확인한 주제 적합성(15점), 관심도 변화(-5~10점)로 우선순위를 매긴다. 단어 포함으로 판단하는 구체성은 조사 후보를 구성할 때만 사용하며 최종 점수에 넣지 않는다. 검색량의 점수 상한을 둔다. 별도로 조회한 공식 페이지만 확보한 후보는 조사 보류 목록(`held`)에 저장하고 자동 발행하지 않는다. 공식 페이지는 검색 순위 표본이 아니므로 `evidence_mode=official_pages`, `organic_provider=null`, 검색 결과·도메인 목록은 빈 배열, 점유율은 null로 기록하고 경쟁 기회 점수는 0점이다. 실측 경쟁도와 혼동하지 않으며 점수 항목을 함께 저장한다.

네이버 월간 검색량은 Google 검색량이 아니다. 광고 경쟁도는 기록만 하며 SEO 난이도로
사용하지 않는다. 검색 결과 도메인 비중 역시 SEO 난이도나 순위를 정확하게 예측하지 못하는
보조 지표다. Google Trends의 완결된 최근 7일 대비 이전 7일 상대 관심도 변화를 조회해 -5~10점으로 보정한다.
표본 부족·조회 실패는 trend_growth=null로 기록하고 가산하지 않는다. CAK 직접 급상승 후보는 자신의 hot/10을 별도 `cak_trend`(최대 10점)로 반영하고 Google 관심도 보너스는 중복 가산하지 않는다. 연관 후보에는 원본 시드의 상승률을 가산하지 않는다. 이는 절대 검색량 증가율이 아니다.
현재 시의성은 측정 가능한 관심도 변화와 공식 자료의 마감 검토로 판단한다. Google Grounding은 실측 검증에서 근거 누락이 반복되어 필수 후보 수집 경로에서 제외했다.

## 검색 수요와 발행 주제 검증 (버전 5)

공식 자료로 글을 쓸 수 있다는 판단과 검색 유입을 노릴 근거를 분리한다. 공식 자료만 확보한
후보는 `held`에 `status=research_only`, `publish_eligible=false`, 고정 `hold_reasons`를 남긴다.
해당 후보가 있어도 자동 발행 큐에는 넣지 않는다. 발행 가능한 후보가 없으면 선정 작업은
보고서를 저장한 후 실패로 종료하며, 오래된 큐나 임의 주제로 채우지 않는다.

충분한 실제 검색 표본이 있는 후보가 공식 자료의 메뉴·상세 설명 부족 때문에 명시적으로
거절되면, 아직 별도 상세 조사를 하지 않은 경우에만 공식 본문을 한 번 더 탐색한다.
이 복구는 키워드당 1회, 카테고리당 최대 2회다. 이전과 URL·본문 해시·전달 본문이 다른
실제 출처가 있어야 같은 검수를 다시 수행하며, 새 출처를 글의 근거로 채택해야 한다.
검색 결과·월검색량·조회 시각은 유지하고 아래 발행 조건을 모두 다시 검사한다.
모델의 거절 코드는 재탐색을 시작하는 진단 정보일 뿐 승인 근거가 아니다.

공식 출처 전용 검색에는 관련 키워드에 한해 `korcham.net`(컴활·워드프로세서 등 해당 기관 자격)과
`korea.kr`(정부정책·지원·환급·보험 등)을 최대 두 도메인만 추가한다. 같은 도메인 힌트를 보완 조사에도
전달하며 검색 횟수나 URL 후보 상한은 늘리지 않는다. 경쟁 검증용 원래 검색어와 검색 표본은 유지한다.
일반 수집과 보완 조사 모두 URL·전체 본문 해시·공백을 정규화한 발췌문 중 하나가 같으면 같은 자료로
취급해 최대 세 출처의 자리를 중복 소비하지 않는다. 서로 다른 본문은 그대로 남긴다.

기획 모델은 대표 출처 `source_index`와 실제 사용한 공식 자료의 `source_indices`를 구분해 반환한다.
검색결과 인덱스인 `serp_indices`와 혼동하지 않으며, 공식 자료 목록은 중복 없는 정수 1~3개로 검증한다.
검색 표본이 있는 기획은 대표 출처를 목록에 포함해야 한다. 선택한 실제 HTTP 본문만 `verified_sources`로
작성·근거 검수까지 전달하고 대표 `source_url`은 유지한다. 기존 응답처럼 `source_indices`가 없으면
대표 출처 한 개를 사용한다. 공식본문 전용 기획의 기존 대표·보조 출처 합산 방식은 세 개 상한 안에서 유지한다.

자동 발행에는 다음 조건이 모두 필요하다.

- 실제 검색 API/엔진 응답의 서로 다른 URL 최소 5개, 도메인 최소 3개.
- 검색 표본에서 정부·대형 사이트 비중 60% 이하. 이는 운영 기준이며 SEO 난이도나 Google 순위 예측값이 아니다.
- 제목과 주된 질문이 실측 검색어 전체의 정보 목적에 답할 것. 모델의 판단은 `scope`와
  `target_keyword`로 기록하며, 더 좁은 질문 또는 홈페이지 이동 목적은 보류한다.
- 서로 다른 도메인 2곳의 검색결과 제목·요약에 질문의 근거가 있을 것. 모델이 지정한
  결과 인덱스와 8자 이상의 인용이 실제 응답에 있는지 코드로 대조한다. 공식 본문 인용은
  검색결과 인용을 대신할 수 없다. 이 검사는 경쟁 글 전체를 읽었다는 의미가 아니다.
- 보고서 재사용과 큐·작성·발행 직전에 같은 검색어·제목·질문·조회일 연결과 원문 근거를 재검증한다.
  저장된 `publish_eligible` 값만 믿지 않으며, 점수도 원래 검색량·검색 표본·추세 값으로 다시 계산한다.

생성된 제목·SEO 설명·본문도 공개 전에 별도 Codex 검수를 거친다. 기획의 주된 질문 전체에
답하는지와 이를 보여 주는 본문 인용을 확인하며, 답변 범위가 좁아졌거나 검수가 실패하면 초안으로
보류한다. 같은 초안 ID를 복구할 때도 이 검수를 다시 수행한다. 의미 일치 판단은 모델의 평가이고,
코드는 실제 검색·본문 인용과 연결을 검사한다. 인용 존재만으로 의미의 정확성을 보장한다고 설명하지 않는다.
`--from-queue`를 직접 실행해도 해당 카테고리에 시장 선정 항목이 있으면 같은 검증을 강제한다.
환경변수 누락으로 이전 시장 큐나 자동 생성 주제로 우회할 수 없다.

예를 들어 `ITQ자격증조회`의 월 6,640회를 장기 미접속 로그인 오류만의 검색량으로 쓰지 않는다.
조회 방법 전반을 다루고 로그인 문제를 보조 절로 넣거나, 더 좁은 키워드를 별도로 실측해 조사해야 한다.
`demand_scope=keyword_total`로 측정 범위를 보존한다.

관심도 변화는 `trend_status=measured`(0% 포함), `unavailable`, `cak_measured`로 구분한다.
관심도 미확인인 상시 질문도 나머지 검색·수요·출처 조건을 통과하면 발행할 수 있지만 급상승으로
설명하지 않는다. CAK 연관어에는 부모 키워드의 상승률을 부여하지 않는다.
보고서의 전체 실측 후보 수·조사 풀 크기·실제 상세 조사 수를 구분해, 일부 조사 결과를 전체 시장
최고점으로 표현하지 않는다. 네이버 광고 경쟁도는 SEO 경쟁 점수로 사용하지 않는다.

`Codex Search Sample Diagnostic`은 main에서 수동으로 운영 검색 경로를 점검한다.
기존 전용 구독 인증을 복원하고 native 응답 필드 개수와 고정 질의 세 개의 실제 검색 표본을 확인한다.
각 질의에 URL 5개·도메인 3개와 최소한의 검색어 관련성이 필요하다. 이는 전체 주제 적합성·
공식 출처 검수나 발행 가능 판정을 대신하지 않는다. 보고서·큐·WordPress는 사용하지 않는다.
간이 관련성만 미통과한 질의는 `no_keyword_overlap`으로 남긴다. 실제 검색 응답 확보와
특정 예시 질의의 관련성은 구분하며, 새 후보는 자신의 정확한 검색어로 전체 검수를 다시 받는다.
선정·발행과 같은 동시 실행 그룹을 사용하며, 끝날 때 갱신된 인증을 저장하고 작업용 인증을 정리한다.

`Blog Keyword Select`의 `search_check_only=true`는 별도의 Google·DuckDuckGo 접근을 확인한다.
검색 전용 `GOOGLE_CUSTOM_SEARCH_API_KEY`와 기존 `GOOGLE_CSE_ID`만 사용하고
Codex 인증·CAK 수집·주제 보고서·큐·WordPress는 사용하지 않는다.
표본 개수와 고정 오류 분류를 출력하며 API 키·요청 URL·검색결과 원문은 출력하지 않는다.
Google이 정확한 Custom Search 오류 메타데이터로 제공한 경우 숫자형 프로젝트 번호도 진단에
포함한다. 이는 키의 소속 프로젝트를 확인하기 위한 것으로 키 값·프로젝트 이름·다른 메타데이터는
출력하지 않는다. 일반 실행에서는 이 숫자 진단이 DEBUG 수준에만 기록된다.
이 점검 성공만으로 주제 적합성이나 발행 가능 여부가 승인되지는 않는다.

## 작성 연결과 보류

선정 결과는 data/category_market_topics.json에 카테고리·검색어·검색량·출처·검색 결과
도메인·점수·탈락 이유·선정 시간을 기록한다. 발행 시에만 선택 카테고리의 후보를 기존 큐에
추가한다. BLOG_REQUIRE_MARKET_TOPIC=1이면 해당 카테고리의 신선한 검증 후보 중 최고 점수를
소비한다. 기존 수동 큐 항목은 보존하지만 예약 시장선정 경로에서는 소비하지 않는다.
선정 실패·자료 미확인·검증 후보 소진 시 기존 큐/임의 외항사 주제로 대체하지 않는다.

선정 결과의 `intent`(독자의 질문), `gap`(본문에서 제공할 구체적인 가치), `source_url`을
큐 → 파이프라인 → 본문 작성기에 전달한다. 작성기는 대표 공식 URL과 기획에 사용한 `verified_sources`의 모든 URL을 다시 읽고,
해당 질문과 표·체크리스트·절차를 작성 프롬프트에 반영한다. 이 경로는 선정 후 Gemini로
출처를 다시 찾지 않는다. 보조 출처라도 사라졌으면 본문 생성 전에 보류한다. 새로 읽은 모든 본문을 작성과 근거 검수에 전달하며 저장된 발췌로 대신하지 않는다. 생성된 제목과 SEO 초점 키워드가
선정한 키워드를 유지하는지도 검사한다.

본문 작성과 검수는 기존 Codex 구독 경로와 편집·출처·대표 이미지 게이트를 사용한다.
시장 주제 본문에 출처 검수 문제가 있으면 검수 의견과 새로 읽은 공식 자료를 이용해
한 번 보완하고 전체 검수를 다시 수행한다. 여전히 문제가 있으면 초안으로 보류한다.
검색량이 높아도 실제 Google 유입·수익을 보장하지 않는다. 이 변경은 새로운 시장 주제 선정이며,
기존 글의 GSC 노출 순위를 후보 생성의 출발점으로 사용하지 않는다.

새 보고서는 `selection_version=5`다. 이전 버전이나 검색 의도·읽은 공식 본문이 없는 캐시는
재사용하지 않는다. 버전 4의 기존 공식본문 전용 후보도 자동 발행에 재사용할 수 없다. `serp`는 실제 검색 결과를 요구하며, `official_pages`는 관측된 검색 활동과
질문에 사용한 모든 공식 출처의 본문·확인일·주소 후보 및 원래 제공 방식의 연결을 요구한다. 조사 요청 하나가 실패해도
이미 검증한 다른 후보는 보존한다. 우선순위 점수는 예상 방문자 수나 Google 순위가 아니다.
독자의 질문에 답하고 검색 결과 대비 추가 가치를 제공한다는 편집 기준은
[Google의 유용한 콘텐츠 지침](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)을
참고하며, 위 숫자와 가중치는 이 프로젝트의 탐색 기준이다.

## 확인만 실행

GitHub Actions → Blog Keyword Select → category=all 또는 특정 카테고리.
이 작업은 글을 발행하지 않는다. 구독 인증을 쓰는 실제 선정 실행은 main에서 수행한다.
main 실행은 생성된 보고서를 커밋한다. 일부 카테고리가 실패해도 다른 카테고리의 검증된 결과는 보존한다. 자동 발행은 기존 Auto Blog Post의 post-queue 작업이다.

`research_check_only=true`는 웹검색 한 번과 공식 본문 접근만 점검한다. 카테고리 보고서를
생성·커밋하지 않으며 기존 보고서도 건드리지 않는다. 실제 검색 활동 없음, 공식 주소 후보 없음,
공식 HTML 접근 실패를 고정된 사유와 도구 이벤트 건수로 구분한다.
`auth_check_only=true`도 지정하면 인증 점검만 우선한다. 두 점검 모두 인증 갱신 저장·정리는 유지한다.

SELECT_TOP_N의 빈 문자열은 2로 처리하며 1~5만 허용한다. 이전 건강/뷰티 전용 스캘폴드 생성은
이 선정 작업에서 제거했다. BytePulse 발행 파이프라인은 변경하지 않았다.

## 한 번 발행한 키워드 재발행 금지

시장 후보 선정, 캐시 재사용, 작성 시작 전, WordPress 저장 직전에 모두 제목/초안/예약 글과 기존 발행
레지스트리를 대조한다. 공백·대소문자·문장부호·연도(2026→2027)만 다른 키워드도 같은
키워드로 정규화한다. HTML 공백 엔티티와 전각 문자 차이도 정규화한다.
새 시장 키워드의 WordPress 발행 응답 직후 posted_market_keywords.json에 키워드와 글 ID를
누적하고 그 다음 부가 핑/레지스트리를 처리한다. 부가 작업 실패로 이미 발행한 키워드의 이력을
누락시키지 않는다. 이 이력은 글을 삭제해도 삭제하지 않는다. 재작성은 신규 포스팅이
아닌 기존 글 갱신 작업으로 별도 수행해야 한다. 동시 발행/선정은 같은 concurrency 그룹으로
직렬화한다. 초안은 중복 방지 대상으로 예약하되 공개 발행 완료로 기록하지 않는다.

WordPress 신규 글 생성 요청은 한 번만 전송한다. 타임아웃·서버 오류·비정상 응답이 나도
서버에는 이미 글이 저장됐을 수 있으므로 자동 재전송하지 않는다. 생성 결과가 불확실하면
WordPress의 공개 글·초안·예약 글을 먼저 확인하고, 이미 생성됐다면 같은 글 ID로 복구한다.
조회 요청의 일시 오류 재시도는 유지한다.

보류한 시장 초안은 큐에 글 ID와 URL을 기록한다. Auto Blog Post에서 `mode=queue`,
해당 `category`, `writer_provider=codex`, `publish=true`, `resume_draft_id=기존 글 ID`로
복구하면 같은 글의 근거를 한 번 보완하고 전체 검수를 다시 수행한다. 이 경로는 새 주제를
선정하거나 새 글을 생성하지 않는다. 원래 선정 시각·출처 만료와 중복 검사는 유지하며,
공개 상태 재조회 후 큐를 완료하고 영구 키워드 이력에 기록한다.

## 분석 모델

시장 후보 분류와 공식 자료 적합성 검토도 CODEX_AUTH_JSON 구독 인증을 사용한다.
실측 검증에서 Gemini 무료 일일 요청 한도에 도달했으므로 이 선정 경로의 Gemini 의존은 제거했다.
선정 job과 발행 job은 같은 concurrency 그룹에서 인증을 복원·갱신 저장·삭제한다.
공개 저장소의 구독 인증은 기존 guard에 따라 main의 수동/예약 실행에서만 허용한다.
검증 브랜치에서는 단위 시험을 수행하고, 실제 인증 검증은 검토·머지 후 main에서 수행한다.

Codex 웹검색은 별도 검색 API 키를 요구하지 않는다. 검색 표본은 고정 버전 0.153.4의
App Server `webSearch.results`에서만 읽으며 `standalone_web_search`와 live 검색을 활성화한다.
전용 인증 디렉터리, 임시 작업 디렉터리, ephemeral 읽기 전용 thread와 빈 도구 환경을 사용한다.
검색 완료 요약만으로는 이미지 검색이나 혼합 작업을 구분할 수 없으므로 실제 함수 호출 인자도
메모리에서 검증한다. 지정 질의 하나의 `search_query`만 허용하고 `call_id`를 같은
thread·turn의 완료된 검색 결과 ID와 대조한다.
`features.code_mode.direct_only_tool_namespaces=["web"]`로 웹 도구를 직접 호출하도록 노출해
중첩 코드 실행의 다른 호출 ID가 섞이지 않도록 한다. 검증할 수 없는 코드 래퍼는 계속 거부한다.
이 검증은 고정 버전의 실험적
`experimentalRawEvents` 필드에 의존한다. 해당 필드는 내부용으로 표시돼 있으므로 지원이
보장된 장기 계약으로 취급하지 않으며, 버전을 변경할 때 단위 테스트와 실제 진단을 다시 통과해야 한다.
검색어가 다르거나 결과가 누락·null·불완전하면 보류한다. 원문 프로토콜이나 임의 오류는 로그에 출력하지 않는다.
별도 공식 자료 보충 조사는 CLI `-c web_search="live"`, `exec --json`을 사용하고
연구 요청에서 셸 도구를 비활성화한다. 읽기 전용 샌드박스와 자격 증명 환경 격리를 유지한다.
설치 버전 0.153.4의 TUI `--search`만으로는 exec 설정이 전달되지 않아 명시적인 `-c`가 필요하다.
또한 이 버전은 app-server의 `openPage` 이벤트를 exec의 `other`로 바꾸면서 URL을 누락할 수 있다.
따라서 native 열람 이벤트만을 필수 조건으로 삼지 않고, 관측된 검색 활동과 별도로 읽은 공식 본문을 요구한다.
검색 이벤트 원문은 로그에 출력하지 않으며, 검증에 필요한 공개 URL과 고정된 상태만 남긴다.
관련 계약: [Codex 웹검색](https://learn.chatgpt.com/docs/web-search),
[비대화형 JSONL 출력](https://learn.chatgpt.com/docs/non-interactive-mode),
[App Server](https://learn.chatgpt.com/docs/app-server).

`candidate_check_only=true`는 CAK artifact의 실제 다운로드 권한과 지표 계약만 검사한다.
Codex 인증을 복원하지 않고 카테고리 보고서·큐·발행 이력을 변경하지 않는다.
인증/웹검색 점검도 선택하면 기존 점검을 우선한다.

## 버전 5 적용 검증 (2026-09-10)

위 세 글은 버전 4에서 발행된 결과이며, 버전 5 기준을 통과한 발행 사례는 아니다.
버전 5의 관련 8개 테스트 파일 482개, Actionlint 1.7.12, `git diff --check`를 통과했다.
기존 실제 보고서의 버전 4 후보 5개가 새 자동 발행 경로에 재사용되지 않는 것도 확인했다.
독립 검토에서 발견한 최종 본문 범위 검사 누락과 직접 큐 실행 시 환경변수 누락 우회를 보완했다.

실제 GitHub runner의 [검색 진단 34452469996](https://github.com/hhj4861/wp-auto-blog/actions/runs/34452469996)은
`search_check_only=true`로 실행했으며, 검색 표본을 얻지 못해 실패 종료했다.

| 기존 설정 | 실제 응답 | 판정 |
| --- | --- | --- |
| `GOOGLE_API_KEY` | Google HTTP 400 / `api_key_invalid` | 현재 검색 키로 인증 불가 |
| 대체 `GOOGLE_AI_API_KEY` | Google HTTP 403 / `api_not_enabled` | 해당 키에서 Custom Search API 사용 불가 |
| DuckDuckGo fallback | HTTP 202 / `challenge` | 검색 결과 대신 차단 응답 |
