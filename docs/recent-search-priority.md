# 최근 검색 상승 우선 선정

## 목적과 데이터 구분

월 검색량 중심으로 후보를 먼저 잘라내면 최근에 뜬 작은 키워드를 조사하기 전에 놓친다. NAVER API HUB 일별 검색어 트렌드를 **후보 선정 전에** 조회하고, 최근 상승과 지속성이 검증된 후보를 먼저 조사·발행한다. 월 검색량은 기본 수요의 보조 지표로 유지한다.

- API: `https://naverapihub.apigw.ntruss.com/search-trend/v1/search`.
- [공식 API 규격](https://api.ncloud-docs.com/docs/naver-api-hub-search-trend): `timeUnit=date`, 결과는 최댓값 100의 상대 지수다. 일별 실제 검색 횟수나 실시간 검색량이 아니다.
- 설정: GitHub Secrets `NAVER_API_HUB_CLIENT_ID`, `NAVER_API_HUB_CLIENT_SECRET`. 기존 `NAVER_AD_*` 검색광고 키와 별개다. [인증 규격](https://api.ncloud-docs.com/docs/naver-api-hub-overview)의 NCP 헤더로 전송한다.
- 키워드마다 별도 그룹에 원문 한 개만 넣는다. 시드·연관어의 상승률을 다른 키워드에 옮기지 않는다. 요청 간 상대 지수의 높이를 절대 수요로 비교하지 않는다.

## 선정 정책

1. KST 어제까지 최근 15일을 요청한다. 당일 데이터는 사용하지 않는다. 실제 반환된 최신 날짜가 어제 또는 그제여야 하며, 해당 날짜와 지연 일수를 기록한다. 최신 10일이 연속으로 존재해야 한다.
2. 최신 하루/직전 7일 평균, 최근 3일 평균/그 이전 7일 평균, 최신 하루/지난주 같은 요일을 각각 비교한다.
3. 초기 운영 기준은 각각 30%·20%·20% 이상 상승, 최근 3일 중 2일 이상이 이전 7일 평균보다 20% 이상 높은 경우다. 튜닝용 정책 기준이며 방문자 증가를 보장하는 통계 모형이 아니다. 기준 구간이 0이거나 데이터가 없으면 무한 상승률을 만들지 않는다.
4. 검증된 상승 후보를 후보 목록·모델의 조사 순서·최종 선정·실제 발행 큐에서 우선한다. 일별 분석을 적용하는 실행의 후보는 조회 성공·실패 모두 월 수요 점수 최대 15점, 최근 상승 점수는 최대 45점이다. 같은 후보에 Google 주간 추세를 중복 가산하지 않는다.
5. 일별 API가 설정되면 월 검색량 10~499회인 **실측 후보**도 조사 입력에 남긴다. 그 후보는 최근 상승 조건을 통과해야 최종 조사 풀에 들어간다. 마스킹·누락 검색량을 0이나 추정 검색량으로 채우지 않는다. 월 500회 이상 일반 후보도 유지한다.
6. 공식 출처·검색 관련성·검색 의도·기존 글 중복·발행 심사는 동일하다. 상승세가 있어도 부정 판정을 덮어쓰거나 품질 기준을 낮추지 않는다.

## 비용·시간·복구와 재사용

- 한 실행 최대 120개 후보·24회 요청, 5개 키워드씩 묶는다. 첫 조사 목록은 월 500회 미만 후보 최대 40개와 일반 후보 최대 80개를 우선 배분하고 빈자리는 나머지 후보로 채운다. 모든 키워드나 인터넷 전체의 인기 순위를 전수 조사하는 기능은 아니다.
- 실제 조회 처리 누적 시간 예산 60초, 요청 timeout 최대 4초, 리디렉션 금지. 실패 원문·응답 본문·인증값은 로그에 남기지 않는다. 인증 실패·호출 한도 오류는 같은 실행에서 추가 API 호출을 중단한다.
- 키 누락·통신 실패·오래된 값은 `not_configured` 등 고정 상태로 기록한다. 해당 후보에 최근 상승 가점을 주지 않고 수요·품질 기준으로 진행한다. API가 설정된 실행에서는 실패 후보도 월 수요 15점 상한을 유지해, 누락 데이터 때문에 오히려 유리해지지 않게 한다. 키 자체가 미설정이면 기존 점수 체계를 유지한다. 최근 추세 기능이 작동했다고 보고하지 않는다.
- 원시 날짜별 상대 지수와 계산 결과를 선정 기록에 저장해 발행 전 재계산한다. 키워드 바인딩·점수·조회 시점 검증을 거치며 KST 날짜가 바뀌면 재조사한다. API가 설정된 상태에서는 일별 근거가 없는 과거 캐시도 재사용하지 않는다.
- 별도 `Recent Search Trend Probe`는 네이버 조회만 수행한다. Codex 인증·모델·발행·큐 변경을 하지 않으며 실제 데이터 날짜와 고정 오류 코드만 출력한다.

## 운영 적용 상태

구현 브랜치 단계이며 main/운영 미반영이다. 작업 시작 시 두 API HUB Secret은 미등록이었다. 실제 API의 인증 성공·최신 데이터 날짜는 키 등록 후 probe에서 검증해야 한다. PR 머지는 사용자 승인 후 진행한다.
