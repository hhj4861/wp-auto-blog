# 텔레그램 답장으로 쿠팡 상품을 넣고 발행하기

쿠팡 링크는 **상품 홍보·추천·비교 등 구매를 돕는 목적으로 명시적으로 지정한 글에만** 사용합니다. 일반 정보글은 링크 요청과 30분 대기를 건너뛰고, 기존 본문·출처·중복·품질 검수를 통과하면 발행합니다. **상품 홍보글의 링크 요청을 성공적으로 보낸 뒤 30분이 지나도 답장이 없으면, 검수를 거쳐 쿠팡 상품 없이 같은 초안을 발행합니다.** 쿠팡 API를 사용하지 않습니다. 이미 발행한 글을 다시 생성하거나 기존 공개 글에 상품을 일괄 추가하지 않습니다.

## 글 유형 지정

자동 키워드 선정 결과는 `article_type: information`으로 저장합니다. 값이 없는 기존 글이나 알 수 없는 값도 쿠팡 사용을 허용하지 않습니다. 기존 광고·레이아웃 소급 적용 스크립트에서도 취업 카테고리라는 이유만으로 쿠팡 박스를 추가하지 않습니다. 카테고리, 상품 언급, 제목의 ‘추천’이라는 단어로 홍보글을 자동 판정하지 않습니다.

편집자가 실제 상품 홍보·추천·비교를 목적으로 기획한 **검증된 시장 키워드 큐 항목**에만 `article_type: product_promotion`을 지정합니다. 이 지정이 출처·검색 수요·상품 관련성 검수를 대신하지 않습니다. 단순 링크 삽입을 위해 정보글을 홍보글로 바꾸지 않습니다.

- 퇴직금 중간정산, 시험 일정·공부법, 기관지에 좋은 음식 같은 일반 정보글: 요청·삽입 없음.
- 구매 선택을 돕는 교재 상품 비교·식품 제품 소개처럼 명시적으로 기획한 상품 홍보글: 아래 요청 절차 적용.
- 기존 비홍보 대기 요청은 보류하고 추가 상품 요청·링크 삽입을 막습니다. 이미 만료됐거나 발행 결과가 불명확한 초안은 자동 재발행하지 않습니다.

## 상품 홍보글 사용 방법

1. 기존 `Auto Blog Post` 예약이 시장 키워드를 선정하고 본문·이미지를 검수한 뒤 WordPress 초안을 저장합니다. 수동 실행은 `mode=queue`, 원하는 `category`, `publish=true`를 사용합니다. `general`도 공개 요청 시 같은 시장 큐를 사용합니다. 임의 `topic`을 직접 입력하는 발행은 검증된 큐를 요구하며 중단합니다.
2. 기존 리포트 봇이 `[쿠팡 링크 요청]` 메시지로 카테고리, 키워드, 주제, 초안 ID와 **쿠팡에서 검색할 상품명·용도·선택 기준**을 알려줍니다. 예를 들어 기출문제집 상품 비교글에서는 해당 시험의 기출문제집 검색어를 제시합니다. 맞는 품목을 자동으로 정하지 못한 주제는 그 사실을 알리고 직접 관련성을 확인하도록 안내합니다.
3. 쿠팡 상품을 넣으려면 쿠팡 파트너스에서 직접 상품을 확인하고 단축 링크를 얻습니다. **가능하면 요청 후 30분 안에, 반드시 그 요청 메시지에 ‘답장’**으로 상품마다 한 줄을 보냅니다. 1~3개가 가능합니다.

   ```text
   실제 상품명 | https://link.coupang.com/a/실제발급코드
   ```

   위 주소는 형식 설명이며 사용할 수 있는 상품 링크가 아닙니다. 상품명 없는 URL만 보내면 형식 수정 안내가 옵니다. `https://link.coupang.com/a/...` 단축 링크만 받으며 쿼리 문자열이 붙은 URL은 받지 않습니다.
4. `Coupang Telegram Replies`가 답장을 확인합니다. main의 `Auto Blog Post`가 성공하면 후속 실행이 요청 후 30분이 되는 시점까지 기다렸다가 처리하고, 10분 간격의 정기 실행도 답장을 확인합니다. GitHub Actions 지연 및 앞선 작업 대기 시간이 더해질 수 있으므로 **30분은 자동 발행을 판단하기 시작하는 기준이며 정확한 발행 시각을 보장하지 않습니다.** 즉시 확인하려면 이 워크플로를 수동 실행합니다.
5. 발행을 결정할 때는 먼저 도착한 답장을 확인합니다. 유효한 상품 링크 답장이 있으면 상품 관련성·표현을 검수해 광고 고지와 `관련 상품 살펴보기` 영역을 넣습니다. 30분이 지났어도 이 확인 때 이미 도착한 유효한 답장은 상품을 넣는 경로로 처리합니다. 답장이 없고 요청 후 30분이 지났으면 쿠팡 상품 없이 발행하는 경로로 처리합니다. **두 경로 모두 본문·의학적 주장, 공식 출처, 원래 키워드 선정 근거, 중복 여부를 다시 검수한 뒤 같은 초안 ID를 공개**하고 텔레그램으로 링크를 보냅니다.

잘못된 형식의 답장은 수정 안내를 보내고 대기하며, 검수에 실패한 상품은 발행을 보류합니다. 이를 답장이 없는 것으로 취급해 쿠팡 상품 없이 발행하지 않습니다. 발행 처리가 시작된 뒤 도착한 답장으로 공개 글을 자동 수정하지 않습니다.

건강 상품의 치료 효과, 가격, 최저가, 시험 합격 보장 등 확인되지 않은 주장은 만들어 넣지 않습니다. 입력한 상품명과 단축 링크가 실제로 같은 상품을 가리키는지, 본인 파트너스 계정의 링크인지는 자동 확인하지 않으므로 직접 확인해 주세요.

검색 안내는 실제 판매 상품을 조회한 결과나 발행 승인이 아닙니다. 자격시험 교재는 시험명·급수·필기/실기·출판 연도를 확인하고, 일반식품은 원재료 등 표시사항을 확인해 선택합니다. 대상포진 초기증상처럼 질병 정보를 다루는 글에는 상품 요청을 보내지 않습니다. 상품 홍보글에서도 치료 효과를 임의로 주장하지 않습니다. 답장으로 받은 상품은 기존 본문 관련성·표현 검수를 그대로 통과해야 합니다.

이미 받은 요청에 검색 안내가 별도 메시지로 추가되더라도 **상품 링크는 원래 `[쿠팡 링크 요청]` 메시지에 답장**해야 합니다. 추가 안내 메시지의 답장은 초안에 연결되지 않습니다. 30분은 초안 생성 시각이 아니라 원래 요청의 전송 성공 시각부터 계산하며, 추가 안내를 보내도 다시 시작하지 않습니다.

## 설정과 검증

GitHub 저장소 Secrets에 `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`를 설정합니다. 현재 리포트 봇과 개인 대화방을 함께 사용할 수 있습니다. 그룹 대화방은 답변 권한을 제한하는 `TELEGRAM_ALLOWED_USER_ID`도 필수입니다. 다른 수신기가 같은 봇의 `getUpdates`를 소비하면 안 됩니다. 기존 리포트의 메시지 발송은 유지할 수 있습니다.

등록된 웹훅이 있으면 수신을 중단합니다. 워크플로가 웹훅을 삭제하거나 다른 봇 설정을 바꾸지 않습니다. `check` 명령은 상품 홍보 큐가 있을 때 인증과 웹훅 유무만 확인하고 답장을 소비하지 않습니다. 일반 정보글만 있으면 사전 점검을 건너뜁니다.

```sh
python scripts/coupang_telegram_worker.py check
```

WordPress 인증은 기존 `WP_GENERAL_*` Secrets를 사용합니다. 발행 전 검수는 기존 `CODEX_AUTH_JSON`과 `CODEX_SECRET_WRITE_TOKEN`을 사용하며, 유효한 상품 답장이 준비됐거나 답장 없이 30분이 지나 발행 대상으로 선정됐을 때 Codex를 설치·로그인하고 갱신된 인증을 저장합니다.

## 대기·실패·복구

상태는 `data/coupang_requests.json`과 `data/topic_queue_general.json`에 기록합니다. 공개 저장소에 봇 토큰, 원문 답장, 채팅·사용자 ID를 저장하지 않습니다. 발행에 사용될 상품명·제휴 링크, 초안 ID, 키워드와 처리 상태는 저장됩니다.

- 링크 요청은 발송 의도를 Git에 저장한 뒤 보냅니다. 전송 성공을 확인하면 그 시각과 메시지 식별 해시를 저장하여 대기 시간을 계산하고 다른 초안과 섞이지 않게 합니다.
- 답장 처리 결과와 발행 의도를 Git에 저장한 뒤 WordPress를 수정합니다. 수신 위치를 다음 번 `getUpdates` 호출에 넘기기 전 반드시 이 상태를 원격 저장합니다.
- 원래 요청의 전송 성공 시각이 없는 기존 대기 건은 30분 경과 자동 발행에 소급 적용하지 않습니다. 대기 시각을 추측하거나 새로 채워 넣어 발행하지 않습니다.
- `notification_unknown`: 요청 전송 결과가 불확실합니다. 자동 재전송하지 않습니다. 운영자가 Telegram의 실제 요청 메시지와 초안을 대조한 뒤 복구해야 합니다.
- `waiting`: 사용자 답장 대기입니다. 전송 성공 시각이 확인되는 새 요청은 30분 경과 후 답장이 없는지 확인한 뒤 발행 대상으로 삼습니다. 잘못된 형식에는 고정 안내를 보내며 수정 답장을 기다립니다. 다른 사람·대화방의 메시지나 이미 처리한 답장은 무시합니다.
- `held`: 선정 후 36시간 경과, 상품/출처 검수 실패, 초안 변경, 또는 이전 발행 결과 확인이 필요한 상태입니다. 원래 선정 시각을 갱신하거나 게이트를 완화해 자동 발행하지 않습니다. 보류 사유를 조사한 뒤 필요한 근거를 새로 검증해야 합니다.
- 30분 대기 규칙은 원래 키워드 선정 근거의 36시간 유효기간을 연장하지 않습니다. 이미 보류·만료됐거나 전송 결과가 불확실한 요청은 이 규칙으로 자동 발행하지 않습니다. 답장 확인이 실패한 경우에도 답장이 없었다고 간주하지 않습니다.
- 요청 전송 후 24시간 이상 지난 건은 답장 유실 가능성 때문에 무응답 자동 발행 대상으로 삼지 않습니다. 수신 대기 메시지가 많아 한 번에 전부 확인하지 못한 경우에도 다음 확인까지 기다립니다. 유효한 답장을 받으면 원래의 36시간 유효기간과 나머지 검수 조건을 적용합니다.
- 이전 실행이 `publishing`에서 끝나면 다음 실행은 보류합니다. 실제 공개 여부를 읽어 확인하고 영구 키워드 기록을 대조하기 전 재발행하면 안 됩니다. 수동 `resume_draft_id`도 링크 승인 절차를 우회할 수 없습니다.
- POST 응답이 유실된 경우 같은 실행에서 해당 ID를 읽어 정확한 공개 본문·메타를 확인할 수 있을 때만 성공 처리합니다. POST를 자동 재전송하지 않습니다.

Telegram은 수신하지 않은 업데이트를 최대 24시간 보관합니다. 장기간 수신 장애가 있었다면 유효한 대기 요청에 다시 답장해야 할 수 있습니다. 모든 관련 Actions는 같은 concurrency 그룹과 `queue: max`를 사용하여 새 수신 작업이 대기 중인 포스팅 작업을 취소하지 않게 합니다.

운영 프로토콜 참고: [Telegram Bot API](https://core.telegram.org/bots/api#getupdates), [GitHub Actions concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).
